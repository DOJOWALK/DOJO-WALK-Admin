# DOJO WALK Admin — Unified Company Flow Migration

Date: 2026-10-22
Target branch: `feature/admin-company-flow-migration-2026-10-22`
Base: `main`
Migration policy: all approved Admin UI, company setup, staff/admin access, service-location flow, dashboard/live operations and security/audit work is consolidated on this single branch and reviewed together in one migration PR. Do not merge this branch or deploy production until the acceptance gates below pass.

## Product outcome

The Admin application is the single Company Control Center for DOJO WALK. The owner can start with one service Area and personally cover multiple responsibilities, while the data model and role boundaries remain ready for national expansion. A menu item or mock UI is not considered complete functionality.

## Unified navigation

1. Dashboard — company overview, operational exceptions and quick actions.
2. Live Operations — embedded in the Dashboard view (not a separate navigation destination); show live/last-known location with freshness labels, walker/booking status, delay/safety alerts and actionable walk details.
3. Bookings.
4. Walker Management / Staff Verification.
5. Customers, Pets, Coupons, Notifications and Support (preserve existing working flows).
6. Service Locations — India → State → District → City → Area → Locality, dependent navigation, search/status filters, record status separated from service status, boundary verification and activation confirmation.
7. Company Setup — company profile, legal/document register, departments/designations, roles/permissions, approval authority, policies/SOPs, audit/change history.
8. Staff & Admin Access — onboarding request, verification checklist, appointment/role approval, generated unique Staff ID, secure login invitation, scope assignment, suspension/deactivation and access review.
9. Security & Audit — permission review, approval history and traceable privileged changes.
10. Settings — only real, wired settings; no false-success actions.

## Staff ID and verification

- Staff ID is an immutable unique identifier generated by the system after an authorized appointment/verification approval; it is not a password and does not itself grant access.
- Keep identity/contact documents restricted to authorized HR/Owner roles. Do not expose sensitive document values in broad lists, logs, or client-visible error messages.
- Login identity, staff record, role, reporting manager and service-area scope are distinct fields/concerns.
- Deactivation must revoke future access promptly while retaining the necessary audit trail.
- Never allow a client-only role check to be the security boundary.

## Role and scope rules

- Owner / super_admin: company-wide oversight and explicit high-risk approvals; protected from ordinary admin deactivation or role downgrade.
- National / functional roles: only assigned functions and approved scopes.
- State, District, City and Area managers: access limited to assigned geographic scope.
- Finance, HR, Support and Operations: least-privilege functional permissions.
- Walkers/partners: only their own profile, assigned walks and permitted work data.
- Enforce authorization in trusted backend/Firestore rules and callable/server functions, not only by hiding UI controls.
- Service activation, refunds, payouts, staff privilege grants and other high-impact actions require explicit authorization and audit events.

## Service location invariants

- Preserve the existing India location data and legacy records.
- Keep boundary verification separate from service activation.
- City and Area activation require a valid verified polygon; Locality does not require its own polygon.
- No radius-only replacement for polygon coverage.
- Validate parent relationships and duplicate identifiers; never silently reparent or bulk-delete existing locations.
- CSV import must be previewable, fingerprinted/idempotent, recoverable after interruption, and tested for large batches before production use.

## Dashboard / live operations invariants

- Live operations are shown within the Dashboard; opening them must not push a separate route as the primary workflow.
- Distinguish verified live GPS, stale/last-known GPS, unavailable location and inferred/possible proximity. Never present an estimate as confirmed presence.
- “My Location” must request permission, handle denied/unavailable states and center the map only after a valid location result.
- Operational actions must validate actor role, booking/walk state and server-side preconditions.
- Do not fabricate metrics or show hard-coded counts as live company data.

## Acceptance gates (all required before declaring complete)

- All affected Flutter screens build and analyzer/tests pass.
- Role/scope access is enforced server-side; negative tests prove cross-Area access is denied.
- Staff ID uniqueness, verification/approval, suspension and audit trail are tested.
- Service Location parent navigation, filters, boundary verification and activation are tested without modifying legacy records.
- Dashboard embeds Live Operations; location freshness/confidence and My Location permission failures are handled.
- Company settings and approval changes persist securely; no UI-only mock is called complete.
- Firebase rules/backend changes are reviewed and tested against the Firebase repository; deployment authentication/IAM is verified independently.
- Exactly one consolidated migration PR is used for this work. Do not merge/delete existing branches or PRs automatically; preserve unmerged work until it has been reviewed and ported.
